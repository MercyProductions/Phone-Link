# iPhone media controls

The Windows **iPhone media** page implements Apple Media Service (AMS) remote commands and timestamped player/queue/track observations. It is not audio streaming, call audio, Siri, or a claim of AirPods/Watch parity. Actual media control remains unverified. Earlier attempts encountered characteristic access denial; the later [staged read-only check](bluetooth-gatt-access-check.md) reached characteristic enumeration.

## Source and implemented scope

The [AMS specification](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleMediaService_Reference/Specification/Specification.html) defines optional Remote Command and Entity Update characteristics. Command support is reported by the media source; an accepted write does not guarantee a player effect. The [reference appendix](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleMediaService_Reference/Appendix/Appendix.html) supplies command IDs and entity formats.

The implementation covers all fourteen defined commands: play, pause, toggle, next/previous track, volume up/down, repeat/shuffle cycling, forward/backward skip, like/dislike, and bookmark. Controls are unavailable until a supported-command notification is received; unknown IDs are never executed. Metadata subscriptions cover the three defined entities and eleven attributes. Characteristics are optional: usable channels can operate independently, and setup failures are reported without inventing missing values. Now Playing shows the independently timestamped title, artist, and album fields received from the phone.

For a truncated observation, select the row and choose **Read full selected value**. This option requires a live session, subscribed Entity Update channel, and the optional readable/writable Entity Attribute characteristic. The app serializes the selector write and uncached read with its other AMS commands, and accepts bounded UTF-8 only while the original observation and player context still match. A result inconsistent with the observed prefix is discarded. This operation requests metadata, not a playback change.

## Workflow and boundaries

1. Select **Scan paired devices**. Discovery probes existing paired BLE devices, reports unavailable probes separately, and lists only AMS advertisers. A name is not authenticated ownership or proof of characteristic access.
2. Explicitly select your own device. There is no automatic first-device selection or fallback to another phone. Startup rechecks the selected Windows device ID against the paired inventory, reuses existing allowed access (requests only if Windows reports Unspecified), explicitly attempts a shared-mode service open, then checks actual characteristics. A denied or failed open is terminal for that attempt, with no exclusive-mode fallback.
3. Setup subscribes for command support and observations. It sends no playback/volume/preference command. Any permission decision remains the user's; the app does not approve dialogs, change settings, bypass access policy, read pairing credentials or install software.
4. Choose an advertised command and review its confirmation. Cancel is the default. Each confirmation creates a session-bound, single-use request. A new, explicitly confirmed request may repeat a command, but the same request cannot be submitted twice.
5. Stop/cancel, navigate away, or lock Phone Link to cancel pending work, close confirmation, clear observations/command knowledge, and release owned WinRT objects. Disconnect or a service change permanently ends that session object. A fresh session is required afterward.

Before starting, you can opt in to **one reconnect after a Bluetooth disconnect** for that session. It is off by default and not persisted. After an initially usable session disconnects, Phone Link first releases its old handlers and GATT objects and clears commands and metadata, waits two seconds, and attempts a fresh shared session for the same paired Windows device ID. It proceeds only if Windows reports existing access as Allowed at both the device and service stages. It does not call the service permission-request API, retry failed characteristic enumeration on this path, or fall back to another device. Reconnection may restore metadata and command-list subscriptions, but never submits a playback command. A GATT service change, failed initial setup, denied or unknown access, failed cleanup, second disconnect, Stop, hide, lock, suspend, or leaving the page does not trigger another attempt. This is an app recovery feature, not a bypass of the observed access denial.

Commands are serialized and recheck session authorization, current availability, and observed context after waiting. Changes to player name, track fields, queue index or the supported command set invalidate a pending confirmation; routine elapsed/volume updates do not. This is a best-effort check of observed context, not an atomic identity guarantee for the phone's active player.

Write-with-response and write-without-response characteristics are distinguished. Results are `NotSent`, `WriteAccepted`, `SubmittedUnacknowledged`, `DeviceRejected` with an available protocol error, or `OutcomeUnknown`. An ambiguous in-flight write is never automatically retried. An already submitted command cannot be recalled. The UI never optimistically changes playback/volume to match a requested command.

## Media delivery check

After scanning and selecting your own phone, choose **Check media data delivery** instead of starting a regular media session. This temporarily uses the same shared-open path with existing Allowed access only. It subscribes to Entity Update and registers one field, Player Playback Info, using the [AMS Entity Update format](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleMediaService_Reference/Specification/Specification.html). It never subscribes to the Remote Command characteristic, requests track/title metadata, reads extended values, or issues a playback command.

After registration is acknowledged it waits up to six seconds for a valid callback, including callbacks that arrived during the registration write. The result distinguishes a valid update from silence, a closed session, missing characteristic properties, and rejected subscription or registration. It displays a classification and an unusable-frame count only; received playback details are not retained, and unsolicited metadata is not decoded. Stop, lock, or leaving the page cancel the attempt; the temporary session is released before the result displays. A quiet check does not diagnose a phone fault or prove remote controls cannot work.

Input buffers and text are bounded, UTF-8 is validated, and truncated/unknown-flag numeric observations are not interpreted as complete values. Non-finite/out-of-range volume and malformed playback data remain unvalidated. Fields arrive independently with individual received times; they are not an atomic now-playing snapshot. No playback clock, progress, battery health or command effect is invented. Metadata remains in memory, is not exported/logged/persisted, and raw incoming byte copies are cleared after parsing. Cleanup does not send a delayed CCCD-disable write or forcibly disconnect other Windows clients; system-level link teardown is not claimed.
