# Bluetooth Messages inbox

On Windows open **Messages**, select your own iPhone in the paired Bluetooth device list, then choose **Read permitted inbox previews**. Phone Link discovers the selected peer’s Classic Bluetooth MAP Message Access Server, requires an encrypted RFCOMM connection, and requests up to 20 inbox previews with a bounded read-only OBEX exchange. The device may return only recent or session-scoped messages, an empty listing, or a permission failure. No message is sent, marked read, deleted, or downloaded as a full body; attachments and live notifications are not part of this path. Inbox rows are not saved and clear on selection change, lock, or navigation.

Multiple MAP instances are not selected arbitrarily. Phone Link consults the advertised message types and only opens a uniquely selected text-message service. The inbox request excludes email, and the parser ignores email rows even if the peer returns them. The active selection, Windows’ service visibility, and the iPhone’s Bluetooth permissions all matter. A CarPlay projection, an ordinary Bluetooth bond, and USB diagnostics do not grant the app the same access.

`PhoneLink.DeviceProbe --bluetooth-profile-check` queries service discovery for up to six paired Classic peers and returns aggregate counts only, without a phonebook or message request. A live Windows probe found one MAP and one PBAP advertisement among two paired peers; it did not attribute the services to a named peer or verify inbox or contacts access. Scripted tests verify the OBEX command sequence, continuation handling, denial, email exclusion, and rejection of unresolved entities. Positive iPhone inbox access and message sending remain unverified. PBAP discovery is not Contacts import.

November 7 live test, standalone build from `963b724`: the explicitly selected paired iPhone returned OBEX `0xC3` (Forbidden) on MAP session open. No folder traversal or inbox-list request was reached. This rules out the inbox XML parser as the cause of this observed failure, but does not identify which setting or platform policy caused the refusal. No previews, device identifiers or message content were retained. Successful Bluetooth phone-book reads on the same setup do not imply MAP authorization.

A separate supported direction for sending is Apple's [MessageUI composer](https://developer.apple.com/documentation/MessageUI/MFMessageComposeViewController): the authenticated companion could present a user-reviewed draft on iPhone. That would require a distinct capability and protocol, would not read the inbox or send automatically, and is not implemented by the MAP feature.

References: [Bluetooth SIG MAP](https://www.bluetooth.com/specifications/specs/message-access-profile/), [Windows RFCOMM](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/send-or-receive-files-with-rfcomm), and [Apple on CarPlay](https://developer.apple.com/documentation/carplay).
