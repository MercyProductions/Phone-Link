# Explicit companion health snapshots

The companion's **Health checks** tab provides a one-time, read-only capture of charge/charging state, low-power mode, thermal pressure and the companion's existing Contacts, Photos, Camera and Notifications authorization states. It does not request permissions, read content from those frameworks, diagnose failed parts or run a repair. Unavailable charge stays unknown; charge is not maximum battery capacity, cycle count, charger wattage or battery health. Thermal state is an OS pressure category, not a temperature sensor reading.

## Phone collection and sending

Capture is explicit and foreground-only in the UI. Battery monitoring is enabled only around a capture and restored to its previous state. Storage capacity available for important usage is estimated separately and displayed only on the phone. The privacy manifest declares disk-space reason `85F4.1`; no storage value or derived storage result is in the network model. The existing UserDefaults reason is unchanged. Background/inactive transitions and leaving the page clear its pending preview/confirmation.

To share, first connect this project's companion to your Windows app. Capture, review the visible values, choose **Review sending to connected PC**, compare the displayed PC installation identity, then confirm the specific snapshot. The intent pins the full authenticated connection (peer/session/endpoint); a changed connection or a capture older than two minutes is rejected. The Windows capability `diagnostics.health.v1` is required. No remote request or background poll triggers a capture. Sending uses existing pinned-TLS authenticated WSS and waits for a correlated/session-bound receipt, without automatic retry. An unconfirmed receipt is not claimed as successful delivery.

The payload includes only schema version, phone-reported capture time, nullable charge percentage, charging state, thermal state, low-power flag and four permission labels. Device identity comes from the authenticated envelope, never from an asserted payload identity. The payload excludes storage, names, identifiers, contacts, photos, logs, health records, microphone/camera samples and Apple credentials. Permission labels describe authorization for this companion, not a guarantee that an operation works; for example, a system photo picker can work without full-library authorization.

## Windows receipt and display

The existing current-session/revocation check runs before the health handler. A snapshot must request an acknowledgement and have no request correlation ID. The handler enforces a 4096-character payload bound, required fields, schema 1, numeric JSON types, known tokens and charge bounds. Unknown fields are rejected. Existing strict envelope validation rejects duplicate keys and malformed JSON before feature handling. Invalid or privacy-blocked input gets `accepted: false`, not a successful receipt.

The inbox holds at most 16 devices' latest snapshots in memory, bound to their authenticated session IDs. No database, log or clipboard persistence is added. Disconnect/reconnect events, app lock and shutdown clear relevant entries; revoked/inactive sessions cannot display them. Receipt age uses Windows time, not the phone's clock. Reports are eligible for retrieval for less than five minutes, and stale/clock-reversed/mismatched entries are removed on access. Expired bytes may remain until an inbox operation or session/privacy cleanup; secure memory erasure is not claimed.

In Windows **Troubleshooter**, **Run connection checks** retrieves available snapshots from active trusted sessions, labeled with a short installation-identity prefix. Capture and receipt times are both displayed; values are a scan-time snapshot, not continuously refreshed measurements. Phone health is separate from USB queries and excluded from the copied connection report. Lock and navigation clear the displayed health text. Elevated thermal pressure produces cautious cooling/resource guidance, not a claim of a defective component or automatic repair.

## Authenticated Windows transport verification

The production health handler is now a reusable `CompanionHealthEnvelopeHandler`, called by the WinUI application's existing inbound pump. It checks the authenticated frame's actor and active session before parsing and rechecks the session after storage. A frame invalidated mid-validation removes only its own session's entry, preserving any newer session's receipt. Receipt construction lives in the handler, so the application and integration tests use identical correlation/session/server-origin/accepted semantics rather than duplicated test logic. The server's outgoing-session check remains in force.

Five real loopback WSS scenarios use the existing native HTTP/WebSocket server, ephemeral in-memory test identities, TLS SPKI pin validation and Ed25519 session proofs. Each verifies capability advertisement, accepted health receipt, malformed/no-ack/correlated/locked false receipts, retained valid data, and eventual cleanup. End conditions exercise repeated message ID, explicit trusted-store revocation plus disconnect, forged origin, wrong session and duplicate nested JSON properties. Rejected transport input closes the connection, and a previously queued frame receives no later health receipt. Eleven focused handler cases cover receipt construction, invalid actors/context/version/kind, invalid requests, and session changes during validation. Sixteen focused cases and the complete 346-test solution suite passed; the final build reported zero warnings/errors. Socket reads and frame waits are bounded.

These tests use a .NET simulated peer, not the installed Swift companion or an owner iPhone. They exercise the production server and health handler, with an isolated test pump and disconnect cleanup, not the entire WinUI AppServices lifecycle. They do not prove iPhone consent UI, physical delivery, populated Windows UI or all operating-system lock/suspend transitions. Those gates above remain open. Identities and certificates are generated test fixtures; no owner credentials or phone data were used, and no certificate trust-store entry or device setting was changed.
