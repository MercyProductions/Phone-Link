# ANCS notification actions and access evidence

The Windows Notifications page implements iPhone-advertised ANCS actions. Physical notification delivery and actions are **not verified**. Earlier Debug attempts were denied characteristic access; a later [staged read-only check](bluetooth-gatt-access-check.md) reached characteristic enumeration. Do not describe this as working call answering, message replies, or majority Watch/AirPods parity.

## Protocol and UI

[Apple's ANCS specification](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleNotificationCenterServiceSpecification/Specification/Specification.html) defines a six-byte action command: command 2, a little-endian notification UID, and action 0 or 1. The phone chooses the meaning of positive/negative actions. ANCS supplies no Data Source action-effect response; an accepted write is not proof of its effect. Identifiers and content belong to one session.

The page shows a button only when the current notification has both the relevant action flag and a usable phone-provided label. Labels are not guessed, truncated, or substituted with generic promises; missing/oversized/control/format-character labels are suppressed. Invalid UTF-8 attributes fail parsing rather than becoming replacement-text action labels. The user must confirm the device, notification and actual label in a dialog whose default choice is Cancel. No automatic action is sent, and this is not arbitrary text reply functionality.

Attribute commands and actions share a serialized Control Point gate. After waiting, an action rechecks the exact current notification object, current app/session authorization and connection. A modified/removed/reused UID invalidates old content immediately. Late attribute replies cannot revive removed entries or attach old action labels to a new revision. Session termination is permanent for that session object; reconnect requires a fresh session. Disconnect and GATT-services changes clear state and cancel pending work. Concurrent Dispose callers share teardown.

Actions have a 15-second cancellation deadline. Each exact displayed revision permits only one attempted action, across either button. This is an app safety policy, not an Apple protocol limitation. A failed/cancelled write may have reached the phone, so it is not automatically or silently resent. An updated notification revision can be reviewed separately. Caller/session cancellation while queued sends nothing. UI navigation, app locking and session end close confirmation and cancel pending action work; a write already submitted cannot be recalled. Windows error codes are retained without notification payload logging.

Results distinguish `NotSent`, `WriteAccepted`, `DeviceRejected` with an ATT error where supplied, and `OutcomeUnknown`. The UI does not optimistically remove a notification or declare an action completed. It reconciles from current session state instead. No native toast action buttons were added; actions are in the app page only.

## Windows access checks

Passive discovery now inspects characteristic properties rather than treating the ANCS service UUID as operational support. Notification readiness requires a notifiable Notification Source. The implemented labeled-action path additionally requires a writable Control Point and notifiable Data Source. AccessDenied is displayed explicitly instead of Available. Discovery itself does not request permissions.

The explicit **Start notification session** action reuses an existing Allowed decision, calls Windows' [RequestAccessAsync](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattdeviceservice.requestaccessasync?view=winrt-26100) only for Unspecified, and does not retry a denial. It opens the allowed service in shared mode before enumerating characteristics. App-service startup preserves the UI context across lifecycle waits/retries because [BluetoothLEDevice.FromIdAsync requires a UI thread](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothledevice.fromidasync?view=winrt-26100). [WriteValueWithResultAsync](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattcharacteristic.writevaluewithresultasync?view=winrt-26100) supplies the write status/protocol error. No permission dialog, privacy setting or OS policy is automatically approved or bypassed. The app manifest already declares the Bluetooth capability; that alone does not prove access for an unpackaged executable.

## Verification

- Debug solution build: zero warnings/errors. Full suite: 208 passed, including 23 added cases (26 total ANCS cases).
- Tests cover wire format, action flags/labels, characteristic access/properties, stale/modified/removed/reused IDs, ended sessions, concurrent duplicate submissions, authorization changes, queued cancellation, ambiguous in-flight cancellation, failed acknowledgments, protocol errors and invalid UTF-8.
- Live Windows UI: page, controls, capability scan and explicit session start were exercised. Windows reported ANCS present but characteristic access denied. After adding the explicit access request, it returned Allowed, but characteristic enumeration still returned AccessDenied. No permission prompt was answered, no notification action was issued and no phone data-changing action was sent.
- Still unverified: populated real-notification action buttons, confirmation/cancel interaction with actual notifications, native Control Point writes, observable phone effects, real service-change/reconnect races and physical app-lock cancellation. Unit tests and XAML compilation do not prove those behaviors.

Next checks: user inspection of the paired PC's iPhone notification-sharing state; compare a current signed package's access behavior without changing OS policy; investigate supported access restrictions and ownership. Microsoft's [notification troubleshooting](https://support.microsoft.com/en-us/windows/apps/phonelink/troubleshooting-notifications-in-the-phone-link) identifies iPhone Share System Notifications as relevant to its product. Its guidance is useful for checking the existing setting, not a guarantee that this custom app will gain access or that this is the observed denial's cause. Do not reset pairing, change security settings or stop unrelated applications as a generic fix.
